# odd-checkbox research comparison

**Inspected 2026-11-20.** Oddkin source baseline `a1-main@2a8c84def4928bca269f559483d8300823ffb080`. The design questions are how to preserve the native form contract, give a caller genuine authority when needed, and distinguish density and visual size without diminishing the target.

## Current Oddkin baseline

- `odd-checkbox` uses a real shadow `input[type="checkbox"]` as its sole interactive semantic node. Its native label wraps the indicator and the default slot. Description and supplied error use the same `aria-describedby` references. Shared styles provide the check and minus glyphs, selected, invalid, disabled and forced-colors treatments, and focus. [Checkbox source](../../../../../packages/components/src/checkbox/checkbox.ts) · [Template](../../../../../packages/components/src/checkbox/checkbox.template.ts) · [Indicator styles](../../../../../packages/components/src/styles/control-indicator.styles.ts)
- `checked` in markup establishes `defaultChecked`. The live `.checked` property detaches from the default on assignment or user action. Native `input` crosses the shadow boundary once with current checkedness. A host-dispatched bubbling, non-composed `change` follows. Property writes are silent. `indeterminate` is separately reflected and cleared on local activation. [Checkable base](../../../../../packages/components/src/form-control/checkable.ts) · [Browser test source](../../../../../packages/components/test/checkbox.browser.test.ts)
- The form association belongs to the custom element. An existing scoped `FormValue` mirrors the effective value and validation into `ElementInternals` after the component updates. It emits submission data only while checked and uses `"on"` as the default value. Reset clears dirty checkedness and touched state. The restore payload holds checkedness, and the current reset and restore paths leave the separate mixed flag alone. Establish a test before claiming stronger same-turn `FormData` consistency than the existing post-update contract. [Form control](../../../../../packages/components/src/form-control/form-control.ts) · [FormValue](../../../../../packages/core/src/controllers/form.ts)
- `odd-switch` shares the checkable base. `odd-checkbox-group` supplies the group label, aggregate required validity and disabled composition. Its children still own and submit their individual values. Neither a checkbox nor a named group currently implements select-all orchestration. [Switch](../../../../../packages/components/src/switch/switch.ts) · [Checkbox group](../../../../../packages/components/src/checkbox-group/checkbox-group.ts)
- The box is currently `1.25rem` in structural CSS and its glyph uses `icon.size.sm`. The label row has a `target.min` block-size floor, `space.sm` gap and `space.2xs` inline inset. `min-inline-size: 0` lets the label shrink beside its fixed indicator. There is no Checkbox `size`, component `density` or strict controlled mode in this baseline. ## Comparison and decisions

| Issue | Observations | Proposed choice and acceptance |
| --- | --- | --- |
| Semantics and events | S1 calls `input` then `change` after successful native activation. I1 mirrors this order and keeps the composed native `input`. I2 supplies a label, helper text and a form-controller bridge with `sl-change` and `sl-input`. I3 can cancel a custom `change` after a local write. I4 shows how to forward intent without a framework-specific public component. | Retain the native checkbox and existing Oddkin `input` then `change` contract in the local path. Follow I1's event shape and existing Oddkin slot and description associations. Test label pointer, Space, one Tab stop, exact event count and order, and no commit for programmatic writes. |
| Initial and live state | S1 keeps a distinct default, live checkedness and dirty flag. I1 resets from the original `checked` attribute. I2's separately exposed `defaultChecked` supports editing the next reset baseline. I3 reflects live checkedness back to markup, so it does not establish native dirty-checkedness semantics. | Preserve `checked` as boolean markup presence, `.defaultChecked` as the baseline and `.checked` as live local state. Probe an attribute change before and after user input, pre-upgrade property writes, reset, and restore. |
| Mixed and submission | S1 uses mixed as a rendering and accessibility bit independent of the boolean submitted value. I3 tests both mixed inputs: a checked mixed input activates to unchecked and an unchecked mixed input activates to checked. I1's tests intentionally exclude mixed values from submission. I2 substitutes `"on"` for empty strings in its adapter. I4 collapses the checked axis into a boolean-or-indeterminate union. | Keep two booleans. Retain checkedness-based submission, including a checked mixed item and explicitly empty `value`. Clear mixed on native toggling and keep it through native-style reset. Tests must inspect both native `checked` and `indeterminate` and `FormData`. Select-all can choose aggregate policy at the host or group. |
| Strict controlled state | I4 splits an externally supplied state from a local default and exposes a change callback. Its basic browser suite does not establish lifecycle races or deferred application outcomes. I3's rollback emits after an internal mutation, which lets listeners observe a provisional write. | Where externally accepted selection is needed, prefer a property-only, discriminated ownership contract with immutable snapshots, native local mode as default, and distinct intent. A form choice without this requirement should use the native path. Decision and a browser acceptance gate are below. |
| Label, description and group | S3's mixed example marks a parent based on child selections and exposes a named group. I2 makes help a slot or attribute. I3 emphasizes group-specific help and distinguishes checkbox selection from an immediate switch. I1's documentation shows external labels and also reports a label-forwarding limitation. | Keep a text label in the existing slot plus `description`/`error` and the existing group. Keep aggregate policy with the host or group. Do not add a second naming channel, group property, focusable helper or bespoke keyboard navigation as part of this redesign. Preserve stable label, description and error IDs across changes. |
| Form and disabled participation | S2 provides FACE and separable restore data. I1 uses that mechanism with form reset and restore. I2 emulates parts of the form boundary through a controller and form listeners. I3's inspected checkbox mixin supplies an internal native control and change but does not demonstrate an equivalent FACE reset and restore contract. | Reuse Oddkin's own `FormValue` and native disabled/required behavior. Keep `name`, optional native form association, `value`, disabled and required. Keep the existing validity delay, label and disabled fieldset behavior. Verify a checked disabled input submits no entry and required invalid feedback appears with its description. |
| Sizing and density | I2 and I3 expose multiple visual sizes. I3 varies glyph geometry with size and retains a labeled native input. I1 separates the touch-target wrapper from visual shape. S4 constrains the actual actionable target, not the visible square. | `size="sm|md|lg"` is useful for explicit visual hierarchy if included in the reviewed spec. Preserve the default visual geometry and existing size vocabulary. Candidate box sizes reuse `icon.size.sm/md/lg` and shared glyphs with existing font/icon values. Keep a clickable label region at least `target.min` in both axes even with a short or missing visual label. Inherit spacing density through `data-odd-density`. Size, density and parent width are independent. |
| Intrinsic layout and continuity | None of the inspected choices requires runtime measurement for a single label. The current row already keeps the indicator fixed and permits the text track to shrink. Inference from S4 and Oddkin allocation rules, a long identifier still needs a safe wrap strategy. | Intrinsic natural-flow primitive. Wrap primary, support and error text, including unbroken strings where necessary. In a multi-line row align the indicator with the first label line. Keep the same focused input, checkedness, validation and focus ring through resize, reflow, theme, size or surrounding density changes. Give bounded parent scrollers ownership; avoid clipping, internal scrolling and width-selected semantics. |

## Ownership, control mode and the controller decision

Ordinary form usage needs no new controller. The browser owns focus, keyboard semantics and activation on the native control. Oddkin already reuses `FormValue` for browser association and validation, and the local checkedness signal is sufficient for an atomic user toggle. A general collection controller would add a source and lifecycle to a single boolean without extending form behavior. Zag is useful evidence for separate writers, rather than a reason to import its state machine or prescribe a framework adapter. Use the existing group for independent choices and keep server or application authority outside the checkbox. This follows the Primitive Architect state and controller review from the workflow checkout.

| Fact | Authoritative owner and lifetime | Transition and reset |
| --- | --- | --- |
| Focus, pointer and keyboard action | Native input within the component instance | Same focusable node across checked, mixed, visual, layout and authority states. Native disabled behavior suppresses user activation. |
| Default and dirty checkedness in local mode | Authored host default and one component-local current value. Default is a separate fact, the reset baseline | Local commits happen at accepted native activation. Programmatic writes set the local value silently. Reset returns to the default and clears touched state. Restore applies the browser's recorded checkedness. |
| Mixed | Local component in native mode. Caller snapshot in external mode | Local activation clears mixed after native preactivation. A controlled snapshot may be mixed at either checked value. Its caller decides whether to accept an intent and what to publish. |
| Effective form value, flags and error association | Derived from effective checkedness, existing `required`/`disabled`/error state and the native form owner via `FormValue` | After the existing update boundary, the real form sees exactly the authoritative checked value. Read before/after reset/restore and protect against a duplicate form entry. |
| Controlled checked and mixed | Application-owned snapshot for one element identity, projected into input and FACE | Requests propose the next values. None commits until the application supplies the next snapshot. On application-owned reset and restore, retain the snapshot until the caller chooses another one; source/browser tests must distinguish both modes. |
| Group selection, aggregate mixed, business validation or save | Existing group composition or host store, with independent browser form owner | Group observes current child values. A server response does not rewrite a checkbox by itself. Application owns requests, persistence, retry, rejection and reconciliation. |

The design candidate for strict control is a property-only union equivalent to `Readonly<{ mode: 'uncontrolled'; checked?: never; indeterminate?: never } | { mode: 'controlled'; checked: boolean; indeterminate?: boolean }>`. The first branch uses the existing host defaults and methods, so there is no second init API. Omission uses the native mode. The wire API name, concrete event naming, and mode-switch behavior belong to the reviewed API contract. A final model must name one owner for the complete checked/mixed pair and have an explicit rule for false values, reset, invalid combinations, attribute precedence and leaving controlled mode. Use a small native-element adapter and the existing form controller if this mode is accepted. Preserve ordinary `.checked` imperative updates in native mode and reject any reinterpretation of the `checked` HTML attribute as a live controlled binding. If the component design has no concrete need for externally accepted selection, document existing property and form behavior and leave a strict adapter as a proposal.

For a strict controlled path, cancel the native input's `click` default before committing and emit one separate typed intent. The input's click is already preactivated when its handler runs, so canonical data should be drawn from the caller snapshot instead of the provisional native flags. Avoid a hand-written Space handler which could double the native click. A synchronous caller acknowledgement must re-project after any canceled-activation rollback. Verify the actual timing and do not infer safety from assigning the inner input synchronously. A missing acknowledgement leaves committed state, validity and form payload stable. Keep native `input`/`change` behavior in local mode. Determine controlled commit notifications explicitly, without mislabeling the request as a commit.

## Operation and draft review

A checkbox has no multistep text draft, submission buffer, component-side transport, backend persistence or command queue. The local transition is synchronous and there is no async response to roll back. Controlled mode, if adopted, emits immutable intent and accepts the latest caller-supplied snapshot. The application owns any pending state and correlation. A deferred action can be refused, implemented as a real in-progress composition, or handled by application policy. The primitive does not infer a pending request from equal boolean values, automatically retry or flag a remote outcome. A busy presentation, a revision, a durable conflict policy and server idempotency are application concerns.

| Operation | Boundary and ordering | Deterministic acceptance |
| --- | --- | --- |
| Native click or Space | Browser preactivation precedes controlled interception or local input. Local mode commits once before its public input listener reads state | Click label or indicator and press Space. Verify one logical activation per gesture. In controlled mode refusal leaves the original input and form value unchanged. |
| Acknowledged change in external mode, if adopted | Application replaces one snapshot. A later publication supersedes earlier values, without latent local writes | Set snapshot synchronously from intent and again after a deferred test gate. Verify final DOM and form data reflect the owning snapshot after activation and commit. |
| Reset, browser restore and reconnect | Browser owns callbacks; the existing scoped controller handles form projection. Local and external states have different write authority | Reset and restore through real form callbacks. Verify effective state, validity and absence of speculative commits. Disconnect and reconnect preserve intentional state and release the old scope, with no stale work affecting new nodes. |
| Save, retry or concurrent persistence | N/A inside the primitive. No requests, request IDs, durable state or remote cancellation | Application integration proves expected-revision checks or transactional guarantees, if used. Run no service-facing claim as part of this component check. |

## Observed native probe and open verification

Ran one Playwright page-level native fixture without Oddkin in Chromium, Firefox and WebKit. A checked mixed box with explicit `value=""` submitted the empty value. Reset restored unchecked while keeping mixed. An actual label click was preactivated and its canceled native input click restored the previous false/mixed flags. An assignment made to the inner input during that canceled handler was itself rolled back. No `input` or `change` followed. This proves the selected native behaviors in those runs, without proving a future controlled adapter, actual assistive-technology announcements, device touch hit-testing or a backend outcome.

Before handoff, verify exact Figma paint and geometry, including one-line and wrapped labels, focus-visible, disabled/invalid/mixed intersections, standard and compact theme density, long content in an actually narrowed parent, RTL, and no overlapping specimens. Current source uses shared control-indicator styles across components. Any change there needs direct impact review. Proposed defaults, event names and ownership require confirmation in the contract and independent browser verification. Refresh this research if form semantics, support floor, source authority or the intended checked-state ownership changes.
