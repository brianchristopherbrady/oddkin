# 0046. Plan audit (2026-10-26): revised decisions

- **Status:** Accepted (2026-10-26, at the owner's request to audit the plan's settled decisions and change any that a better option beats; nothing is released, so compatibility with earlier decisions is not a constraint)
- **Date:** 2026-10-26
- **Area:** Platform | Components | Agent | Process
- **Detailed contract:** [IMPLEMENTATION_PLAN.md](../../../IMPLEMENTATION_PLAN.md) §5e, §5i, §6, M8, M10, M11, §8.2, §9, §11

## Context

The plan is followed as written by four implementing agents, so a weak decision is repeated across every component
they build. The owner asked for the decisions to be re-examined against the project's goals (performance, future
proofing, AI usability, ergonomics; DRY first) with breaking changes free of cost. The audit read the plan's
summaries, milestones M8–M12, §8 and §9, the ADR index (0001–0045), component-contracts.md §2, the feature registry
with the pinned `web-features` 3.43.0 data, the size report, and the lane state on 2026-10-26.

## Decision

**D1. Browser floor: Baseline 2024.** The floor becomes Chrome and Edge 130, Firefox 132, Safari 18.2, and their mobile
equivalents: the versions that support every feature `web-features` 3.43.0 lists as newly available by 2024-12-31
(691 features; `node scripts/compat/baseline-floor.mjs 2024-12-31`). Policy: the floor is the Baseline year that is
Widely Available (30 months after newly available) at or near the v1 release, re-resolved for each release and never
lowered for one feature. ADR 0009's process (pinned data, registry, gates, lint, floor probe) and ADR 0038's
categories stay; ADR 0009's version list is replaced. Features the registry gates, defers, or declines today and that
the new floor covers become foundation candidates, each re-tested before its gate is removed: `@starting-style`
(newly available 2024-08-06), `text-wrap: balance` (2024-05-13), `scrollbar-gutter` (2024-12-11), registered custom
properties (2024-07-09), relative colour syntax (2024-09-16), and `light-dark()` (2024-05-13). The generator's
`ABOVE_FLOOR_SYNTAX` list and the JavaScript library target are re-derived from the same data. The popover
light-dismiss floor exception (Safari iOS 17.0–18.2) still applies at 18.2. Until the re-resolution lands, the
tooling enforces the previous floor.

**D2. `light-dark()` for colour tokens: re-opened, decided by measurement.** It was declined because Safari 17.4
lacked it (css-architecture.md §4). Measure the generator emitting each mode-dependent colour token once as
`light-dark(<light>, <dark>)`, with mode scopes setting `color-scheme`, against today's per-mode re-declaration:
gzip bytes of `tokens:default.css` (3,067 of 3,072 B on 2026-10-26), nested mode scopes across shadow roots, products
with modes, forced colours, `resolveToken`, inspection and DTCG parity, and Theme Studio regeneration. Adopt it for
colours if it is smaller and equivalent; values that are not colours keep the mode toggles.

**D3. Composition schema: go.** It waited for an M8 go with two use cases; it has them: agents generating interfaces
as structured output, and Workbench's saved compositions (M11), with the AI package's `data` part renderer
(ai-interaction.md §5.6) as a third. `@oddkin/components/composition` provides per-element JSON Schemas generated
from the published metadata (properties, attributes, children and slots, action events), `validateComposition()`
and `renderComposition()` over an allow-list of registered elements, and no executable values. It stays out of
ordinary component graphs. An A2UI catalog adapter follows once A2UI 1.0 is published.

**D4. Comparative performance evidence before the catalog grows further.** The §8.2 authoring and rendering suite
(native, Oddkin, Lit, FAST, Svelte 5, Solid, React 19 with and without the React Compiler, Vue 3.5, Angular
zoneless) and the component suite (input and form, dialog, themed region) run now, pinned, in three engines. Their
results set the core size and update-time targets; until then no core budget is raised (the counter is 9,531 B gzip
of a 9,728 B budget, raised once by ADR 0031), and a change that needs more bytes reports where they go. Oddkin
claims no performance lead without the published comparison.

**D5. Foundation semantics before more catalog.** The open §3.1 items (the binding-value matrix, template lifecycle
and node ownership, ordering examples, event semantics) and §3.2 (error ownership) are reconciled with M3's evidence
and finished by the core lane next: about fifty elements already depend on them, and a change costs least now.

**D6. Version-matched agent documentation inside every published package.** The agent kit
(`scripts/agent-kit/kit.mjs`) is generated during the build into each component package (an `agent/` directory with
the entry guide, references, and JSON, plus `llms.txt`) and listed in `files`; `verify-packs` checks it against the
packed metadata. Coding agents read `node_modules`: a kit in the tarball always matches the installed version and
needs no extra tool (`@oddkin/core` already ships `CONTRACTS.md` and `contracts.json`). `@oddkin/agent` remains the
operations layer.

**D7. `@oddkin/agent` starts now, read-only first, on the official MCP TypeScript SDK.** Find and inspect
components, validate usage, and look up tokens and recipes over the analyzer's outputs, as a CLI and an MCP server;
the implementing agents use it while they build, which is its first evaluation. The SDK is a dependency of the
Node-only package (§2.1 allows dependencies in Node tooling); no protocol is reimplemented. Operations that write
(scaffolding, migrations) stay in M11. This settles §9 "MCP adapter implementation".

**D8. Figma Code Connect generated from the catalog.** Code Connect template files for every built family are
generated from `design/figma/reuse.json`, the catalog's Figma-family table, and the metadata (Figma variants to
attributes, text layers to slots), so Dev Mode and Figma's MCP design context give designers and design-to-code
agents Oddkin markup instead of generated code. Code Connect documents web components through its HTML support and
template files (its maintained path; v2.0.2), and needs an Organization or Enterprise plan with a Dev Mode or full
seat. Publishing writes to the owner's Figma organization: agents generate and validate; the owner publishes.

**D9. Optional lazy autoloader.** An opt-in `@oddkin/components/autoload` entry registers each `odd-*` tag on its first
appearance in the document (and in shadow roots it is asked to observe) by importing that tag's `define/<name>`
entry, so markup written by people or agents works without per-element imports and loads only what is used.
Per-element `define/*` imports stay the recommended production path; the autoloader is measured (requests, time to
defined) and covered by the packed consumers.

**D10. Declarative shadow DOM for first paint (M8 experiment).** Prerender display elements' first render into
declarative shadow roots at build time for content pages (docs, examples); elements still replace the root on upgrade
(core-contracts.md: hydration is not supported). Measure LCP, CLS, and the replacement cost against upgrade-only
pages; adopt for the docs and document the pattern if it wins. Hydration stays deferred.

**D11. Lifetime runs per element measure the component scenario.** `research/benchmarks/lifetime/run.mjs` takes
`--scenario <names>`; a per-element run uses `--scenario componentCycles` and writes
`research/benchmarks/.build/lifetime-partial.json`, and the full four-scenario run (dated results file) happens at
round end. The application, navigation, and theme-edit scenarios do not change when an element is added.

**D12. Plan hygiene, because agents load the plan as context.** §9 marks the rows implementation has settled, the
2026-10-17 status section is labelled as a snapshot, and §11 names the current work (this change). At the round-6
boundary, §10 (111,942 of the plan's 454,881 characters) moves to `docs/progress-log.md` and the inline evidence of
`[x]` items becomes a link to verification.md, with the prompts' anchors updated in the same change. ADRs still
marked Proposed whose decision is implemented (0006, 0010, 0012–0015, 0019) are accepted after their Decision
sections are checked against the code.

**Reviewed and kept:** one reactive graph with the binding rule (ADR 0002; external stores interoperate through
`ExternalSource`, and the TC39 Signals proposal is watched rather than followed before Stage 3); `OddkinElement.with()`
(ADR 0003); `Scope` ownership (ADR 0004); runtime tagged templates with no compiler (ADR 0005: no build step and
legible to agents; template precompilation only if D4 shows parse cost); Shadow DOM with shared constructed sheets
(ADR 0008); the cascade layer order (ADR 0039); the TypeScript 5.9 analyzer front end until TypeScript 7's API is
stable (ADR 0018); standard CEM plus separate enrichment (ADR 0017); sRGB hex token output with P3 behind a gate
(M9); no registered custom properties for tokens (registered initial values mask `var()` fallbacks); iframe-isolated
previews and Worker theme generation; the API vocabulary order (ADR 0045); no third-party runtime dependencies; the
data grid on hold (owner).

## Alternatives considered

- Keep Chrome 125, Firefox 126, Safari 17.4 until the M12 re-resolution — fifty components would keep gates and
  floor workarounds the release floor no longer needs, and new components would copy them.
- Baseline Widely Available on the decision date — tracks the date of the decision, not of the release.
- Baseline 2025 — its features are Widely Available only from 2028.
- The composition schema after M8 — delays the agent use case although its two use cases exist.
- Hand-written Code Connect files — a second copy of the catalog mapping; generating them is DRY.
- One entry that registers every element — loads the whole catalog eagerly; the autoloader loads what a page uses.
- An original MCP implementation — protocol work with no product value.

## Consequences

- Assignments: D1 and D2 go to the lane with capacity in round 6 (Agent 2, whose queue is done); D5 to the core lane
  (Agent 3) after its queue; D3, D4 (its research-only dependencies need an announced, owner-approved
  `npm install`), D6, D7, D8, and D9 to round 7; D10 to M8; D11 applies now; D12's move at the round-6 boundary.
- D1 changes the compatibility evidence: the registry, matrix, floor probe (Chrome for Testing 130, Firefox 132), and
  css-architecture.md §2 are regenerated in one change by one lane, announced, because every lane's `npm run compat`
  reads them. Safari 18.2 runtime evidence needs a macOS host, as Safari 17.4's did.
- D3, D6, D7, and D8 add generated artifacts; each is generated from the published metadata, never hand-maintained.

## Revisit when

D1: a required feature needs a newer floor, or the v1 date moves past mid-2027 (then Baseline 2025 is considered).
D2: the measurement shows no saving or an inequivalence. D3: A2UI 1.0 differs from its candidate. D4: the comparison
shows Oddkin behind on a measured axis (then core work precedes catalog work). D9: the autoloader's measured cost
exceeds explicit imports by a margin the docs cannot justify. D10: the experiment shows no LCP gain.
