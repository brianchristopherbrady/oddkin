# 0048. Libraries not built with Oddkin: the standard-CEM baseline, enrichment, and metadata adapters

- **Status:** Accepted (§1 and §2 implemented; §3 and §4 decide the direction, nothing is built)
- **Date:** 2026-10-30
- **Area:** Metadata, Workbench, change impact, agent kits
- **Detailed contract:** [libraries-without-oddkin.md](../libraries-without-oddkin.md); IMPLEMENTATION_PLAN.md CF.3; the [technical plan](../../../future_plans/TECHNICAL_COMMERCIALIZATION_PLAN.md) Workstream B

## Context

Workstream B asks the tools to work on a team's own component library, not only on Oddkin's. The analyzer recognizes Oddkin-authored components only: `OddkinElement` subclasses and `compose()` definitions. On 2026-10-29 Workbench documented a library from its standard Custom Elements Manifest. Whether change impact worked from a manifest alone was unknown, and the kits needed `oddkin.metadata.json`. Other ecosystems describe components in their own formats: the standard CEM analyzer's output, Storybook stories, DTCG token files, and framework docgen output. Each could feed the same tools if read honestly.

## Decision

### 1. The standard manifest is the baseline, read directly by every tool

Workbench, `oddkin-impact`, and `oddkin-kit` read a package's `customElements` manifest without any adapter. From it they take the components, their API, and each tag's registration. Change impact also hashes each class's published module. What the manifest does not state stays absent and is labelled as missing, never inferred. Workbench shows "Not documented" and names the input that would supply the item. A report lists each affected component that no example or suite checks as a coverage gap. A kit says that property-only values, event intents, guidance, examples, and verification are unknown. No tool claims an artifact it did not read.

### 2. One registration rule

Workbench and the kits name the same registration entry. It is the package export that reaches the module holding the tag's `custom-element-definition` export, resolved as Node resolves `exports`. Otherwise it is the shortest export of a module that re-exports from that module. Otherwise there is none. The analyzer keeps a copy of Workbench's `exports` resolution, because Workbench's data layer must not import the analyzer, and a test compares the two.

### 3. Enrichment for a library not built with Oddkin

Enrichment stays a separate, optional layer keyed by stable ids, which joins the manifest by tag. A library not built with Oddkin may publish the layers it has, without component definitions. The first layer to support is examples (`examples.v1`), because examples are what change impact needs before it can select checks. Example files already exist apart from the authoring library: `defineExamples('tag', …)` names a tag, and the analyzer reads the file by parsing it. The missing pieces are:

- an analyzer mode that reads example files against the package's published manifest, instead of warning that it did not register the tag, and that never writes a manifest of its own;
- kits that take components from the manifest when `oddkin.metadata.json` describes none of them, marking those components as described by the manifest alone.

Authored pages (`oddkin.docs.ts`) already work in Workbench for any library. The kits should show them too. Component guidance written as JSDoc tags stays an Oddkin analyzer feature.

### 4. Adapters for other metadata sources

An adapter is a static reader. It converts another source into a contract Oddkin already has: a CEM, `examples.v1`, `docs-content.v1`, `product.v1`, or a token inspection. It adds no new output shape. Its rules:

- It never executes the library's code.
- Every fact it writes names the adapter and the source file.
- Ids come from stable source facts (a story id, a token path, a tag), never from positions.
- It writes nothing it cannot read from the source.
- Renames still need migration records.
- Each adapter has fixtures and known answers, like the analyzer's.

Adapters live in `@oddkin/analyzer` as Node-only subpath entries, and consumers' runtime code never loads them. They are built when a pilot needs one, in this order of evidence:

1. **Existing CEM generators.** No adapter: teams keep their generator, such as the standard analyzer for Lit, Stencil, FAST, or plain elements, and the tools read its output (§1). Oddkin does not write its own manifest generator for code it did not author.
2. **Storybook stories to `examples.v1`.** Read a story file's `component` and the stories whose args are literals. Stories with computed args are listed as present but without values, as the analyzer already does for examples.
3. **DTCG token files to a token inspection.** This gives change impact token items for a library whose tokens are not generated by `@oddkin/tokens`. It finds no edges from tokens to components unless the styles' reads are known.
4. **Framework docgen output** (react-docgen, vue-docgen-api, Compodoc) to a CEM-like API. Only where the static evidence states the API (Workstream B task 5).

## Alternatives considered

- **Require `oddkin.metadata.json` from every library.** Rejected: that is the barrier Workstream B removes.
- **Write an Oddkin manifest generator for code not built with Oddkin.** Rejected: the standard analyzer already does this, and teams already run it.
- **Execute a library's modules to discover facts** (registrations, defaults, or stories' args). Rejected: the tools never execute analyzed code. Workbench's previews run code in frames to show it, not to read facts.
- **A plugin for the standard analyzer that writes Oddkin enrichment from JSDoc tags.** Deferred: examples matter more for checks. A plugin can come later as an adapter under §4.
- **Let the kits import Workbench's `exports` resolution.** Rejected: the dependency would run the wrong way. A parity test keeps the two copies equal instead.

## Consequences

- A library not built with Oddkin gets a catalog with live previews, an impact report with classified changes, and an agent kit, all from its manifest. None of them invents a fact.
- Until §3 is built, such a library has no examples in any tool. A change selects no checks, and the report says so.
- Two copies of the `exports` resolution must stay equal. The parity test fails when they differ.

## Evidence

- Workbench: `e2e/workbench-packed.spec.ts` (`@plain/widgets` from tarballs); `packages/workbench/test/data.test.ts` (pages and labelled gaps); `packages/workbench/test/node-inputs.test.ts` (registrations).
- Change impact: `packages/analyzer/test/impact.test.ts` ("a library described by a standard CEM alone"), with 3 of 3 mutations killed.
- Kits: `tests/agent-kit/standard-cem.test.ts`, with 4 of 4 kit mutations killed. Both parity mutations were killed too.

## Revisit when

- A pilot team's library needs an adapter, or needs examples (§3).
- The standard manifest schema gains fields the tools should read.
- Workbench's `exports` resolution changes. Change the analyzer's copy in the same commit.
