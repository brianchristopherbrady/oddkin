# @oddkin/workbench

Metadata-driven documentation tooling for any custom-element library. **Status:** the DOM-free contract entries, the data files, the shell, panels, isolated previews, Theme Studio, and the Node tooling (`oddkin analyze`, `oddkin workbench dev`, `oddkin workbench build`) exist (design: [workbench.md](../../docs/architecture/workbench.md) §2.1 and §5.1).

**Stability:** Workbench is versioned `1.0.0` with the other Oddkin packages, but its own contracts are **not frozen by 1.0.0** ([ADR 0047](../../docs/architecture/decisions/0047-m8-checkpoint-candidate-v1-contracts.md)): the configuration (`workbench-config.v1`), the page registry (`page-registry.v1`), authored content (`docs-content.v1`), example links (`share-payload.v1`), Theme Studio compositions (`theme-studio-composition.v1`), the preview frame protocol, and the conformance suites and results (`conformance.v1`, `conformance-result.v1`). Until they are frozen they can change in a minor release ([release-process.md](../../docs/release-process.md) §1). The format `defineExamples()` writes, `examples.v1`, is a candidate v1 contract.

| Entry | Contents |
| --- | --- |
| `@oddkin/workbench/examples` | `defineExamples(tag, examples)`, typed from `HTMLElementTagNameMap` (unknown property keys and wrong value types are compile errors); `toExamplesJSON` (the `examples.v1` serializable layer, with fixtures reduced to `hasFixture`); `checkExamples(set, contract)` for plain-JavaScript authors; `exampleId` |
| `@oddkin/workbench/config` | `defineWorkbenchConfig`, `resolveWorkbenchConfig` (defaults and diagnostics matching `workbench-config.v1`), `defineDocs` (`docs-content.v1`) |
| `@oddkin/workbench/pages` | `buildPageRegistry({ config, cem, metadata?, docs? })` producing `page-registry.v1`, plus the projections every navigation surface uses: `primaryNavigation`, `sidebar`, `cards`, `searchEntries`, `onThisPage`, `href`, `resolveLegacyRoute`, `staticRedirects` |
| `@oddkin/workbench/data` | `buildWorkbenchData({ config, libraries, docs?, tokens?, diagnostics? })`: one or more packages' CEM and enrichment, authored content, and a token inspection → a small index (registry, branding, libraries, diagnostics) and one data file per visible page (`pageFile(id)`), serialized byte-stably with `serializeData`; `createImportMap(packages, { base, versioned?, conditions? })` builds import maps from package `exports`, and `resolveExport` resolves one subpath to its file |
| `@oddkin/workbench/node` | Node only. `buildWorkbench({ config?, events? })` loads `oddkin.config.*` (TypeScript through Node's type stripping), the documented packages and their dependencies, their manifests, enrichment, and referenced token inspection, and authored `oddkin.docs.*`, and returns the data files, both import maps, and the shell page; `buildStatic` (`workbench build`), `shellPaths`, `startDevServer`, `writeGenerated` (the marked `.oddkin/workbench/`), `loadWorkbenchConfig`, `loadInputs`, `packageGraph`, and `run` (the command) |
| `@oddkin/workbench/testing` | `mountExample(set, name, container?)` runs an authored example and its fixture in a browser test; `runConformance` runs a conformance suite with the project's own `expect` |
| `@oddkin/workbench/panels/{catalog,component,foundation}` | The embeddable panels' classes; `…/define` registers `<oddkin-catalog-panel>`, `<oddkin-component-panel>`, or `<oddkin-foundation-panel>` (see [Embedding the panels](#embedding-the-panels)) |
| `@oddkin/workbench/frame` | The preview frame runtime, imported by the frame document |

The examples, config, pages, and data entries import without a DOM and have no runtime dependencies (`@oddkin/core` is used for types only). Shipped component code never imports them; colocated `*.examples.ts` files may, because they are development-only sources excluded from the package build (ADR 0021).

## The `oddkin` command

```sh
oddkin analyze <tsconfig.json> [options]     # @oddkin/analyzer's own command, same options and exit codes
oddkin workbench dev [--config <file or directory>] [--port <number>] [--host <name>] [--no-watch]
oddkin workbench build [--config <file or directory>] [--out <directory>] [--base <path>] [--routing history|hash]
```

`workbench dev` serves the Workbench at `http://localhost:4175/` (the configured base path): the shell for page paths (history mode; in hash mode only at the entry, like a static host without rewrites), the data under `_oddkin/`, and package files under `_oddkin/m/<name>@<version>/`. It writes the same data into `.oddkin/workbench/`, a directory it marks and owns, watches the configuration, content, manifests, metadata, and the packages' files, and pushes an `update` event over Server-Sent Events (`_oddkin/events`) after each rebuild. An invalid edit keeps the last valid data and reports diagnostics. Exit codes: 0 success, 1 errors, 2 usage.

`workbench build` writes the same layout as files for a static host, by default into `.oddkin/workbench-build/` (marked and owned like the dev directory; an unmarked directory is refused): the shell, `_oddkin/` data and frame document, and each package's published browser files (no type declarations, sources, or source maps). `--base` and `--routing` replace the configuration's `hosting` values. In history mode every page path and legacy path is a copy of the shell, so deep links and refreshes load on a host without rewrites, and `404.html` is the shell for hosts that serve it; legacy paths redirect in the app, keeping their query. Hash mode writes the shell once. Nothing is written when the configuration or metadata has errors; an import-map target that a package does not publish is a `node.build.unpublished` warning. Output is deterministic, and a rebuild rewrites only changed files and removes stale ones. Theme Studio generates in the browser, so the result needs no Node or analyzer backend.

## Embedding the panels

A site that renders its own pages can show the catalog, component, and foundation panels without the Workbench shell; the Oddkin docs site does (`apps/docs`). The contract is not frozen by 1.0.0 (see Stability above); `e2e/workbench-embed.spec.ts` checks it with a page of its own in three browsers.

1. **Build the files in Node.** `buildWorkbench({ config, hosting: { basePath } })` from `@oddkin/workbench/node` reads the configuration (`oddkin.config.*`, and authored content in `oddkin.docs.*` beside it), the documented packages, their metadata, and their authored examples. `embedFiles(build)` returns every file the panels and previews load, as paths below the base path, each a string or `{ source }` (a file to copy):
   - `_oddkin/index.json`: the index (registry, branding, libraries, diagnostics), the panels' `index`;
   - `_oddkin/pages/…json`: one file per visible page, named by `index.pages[id]`, the panels' `page`, with each example's values (read in Node from the `*.examples.ts` sources; a browser cannot build them; for an installed package, which ships no sources, the values its `oddkin.metadata.json` records);
   - `_oddkin/examples/<tag>.js`: for a component whose examples have fixtures, its `*.examples.ts` source with the types stripped, which a frame imports to run the fixture of the example it mounts (the page file names it as `exampleModule`). Fixtures that write markup with `innerHTML` need a frame without enforced Trusted Types, or a policy the site chooses. When the module is not served or a fixture throws, the frame keeps the element and the panel says that the example's setup did not run;
   - `_oddkin/frame.html`, the preview frame document, and the import maps as JSON: `frame.importmap.json` (the documented packages and the frame runtime) and `shell.importmap.json` (also Workbench's own entries, the panels included);
   - `_oddkin/theme-studio.worker.js`, Theme Studio's generator;
   - `_oddkin/m/<name>@<version>/…`: each package's published browser files.

   Serve them at `<basePath>_oddkin/…`, the URLs `oddkin workbench dev` uses. A `node.build.unpublished` warning names an import-map target that a package does not publish.
2. **The frame document.** Previews run in same-origin frames, one realm each. `_oddkin/frame.html` loads the theme stylesheet, maps the packages with an inline import map, and starts the runtime with an inline module script (`import "@oddkin/workbench/frame"`); its body is `<main data-oddkin-preview>`. A site whose policy allows no inline script or style writes its own frame document with the same parts: an element with `data-oddkin-preview`, the theme's stylesheet, an import map that resolves the documented packages and `@oddkin/workbench/frame`, and a module script file that imports `@oddkin/workbench/frame` (`apps/docs/frame.html`). The runtime imports each component's registration entry by its bare specifier through that import map: the `registration` of its `oddkin.metadata.json` entry, or, for a library with a standard Custom Elements Manifest only, the module whose exports hold the tag's `custom-element-definition`, reached through the package's `exports` (the page file names it as `registration`). The host adds `frame` and `generation` query parameters to the frame's URL.
3. **The host page.** Import the registrations (`@oddkin/workbench/panels/catalog/define`, `…/component/define`, `…/foundation/define`) with a bundler or through an import map (`shell.importmap.json` maps them), load a theme stylesheet (the panels read Oddkin tokens), and set the panels' properties from the files above.
4. **Policy.** Previews need `frame-src 'self'`, and the data fetches `connect-src 'self'`. The panels render with Oddkin's template engine, which works under `require-trusted-types-for 'script'` with `trusted-types oddkin-template`, and need no inline script or style; only the generated frame document has them.
5. **Panels.**

   | Element | Properties | Events and methods |
   | --- | --- | --- |
   | `<oddkin-catalog-panel>` | `index`; `href(route)`, which maps a Workbench route such as `/components/odd-button` to the site's URL for it; `groups`, the categories to list (unset: all); `preview(page)`, a live preview node for a card, the same node for the same page (cards load no component code without it); `query`; `category` | `oddkin-catalog-filter` (`detail: { query, category }`, bubbles, composed) when the reader filters, for the site to mirror in its URL |
   | `<oddkin-component-panel>` | `index`; `page`, the component's page file; `href`; `frameUrl`, the frame document's URL (empty: no preview); `layout`, `'workbench'` (default) or `'reference'`, the documentation page: links to the page's sections, the interactive example without Workbench's preset, preview settings, example link, and event log, and absent items left out instead of labelled; `examplePreview(page, exampleId)`, a live element for an example card, which only a host that loads the library can supply | `previewState` and `previews` (read-only); `replacePreview()` loads fresh frames after the component's code changed. Copy example link (Workbench layout) writes `href(route)` with a `preview` query parameter, which a panel reads when it loads |
   | `<oddkin-foundation-panel>` | `index`, `page`, `href` | — |

6. **Ordering.** A frame handles requests one at a time, in the order they were sent, and `createIsolatedPreview` sends each one after the previous one has settled (its timeout counts from then). An edit made while a preview still loads its module graph applies to the element that mount creates.

## Registry rules

- **Inputs:** standard CEM is enough for the Components baseline, previews included when a module the package exports holds the element's `custom-element-definition`. `oddkin.metadata.json` enrichment adds foundations, categories, examples (with their values when the analyzer could read them from the source), products, and `docs` facts. Authored content (`defineDocs`) overrides prose and presentation only; generated facts win.
- **Stable ids:** `foundations/<slug>`, `components/<tag>`, `theme-studio`, `products`. Routes and the base path can change without changing ids.
- **Honest absence:** a foundation page appears only when enrichment declares it and at least one section has data. Foundations stays as a destination with `availability: 'unavailable'` when no foundation data exists. Components without enrichment are `partial`. Authored `visible: true` cannot show a page or section whose data is missing.
- **Theme Studio** is a primary destination and never a Foundations card or sidebar entry. **Products and modes** is absent unless enabled, and hidden with `pages.products.empty` when no products resolve.
- **Dates** come only from authored content or enrichment facts (authored or source history); unknown dates are omitted and build time is never used.
- **Legacy routes:** `/playground` → `/components` (or `/components/<tag>` from `?component=`, keeping other parameters); `/foundations/theme-studio` → Theme Studio; `/foundations/products` → Products, or a `products.disabled` notice.

Tests: `test/pages.test.ts` (real analyzer output for `examples/core-counter` plus an independent fixture library, validated against `page-registry.v1` and `oddkin-metadata.v1`), `test/data.test.ts` (the published outputs of `@oddkin/components` and `@oddkin/ai`, the default theme's token inspection, the Acme fixture, and import maps from real package `exports`), `test/node-*.test.ts` (throwaway projects with an Acme library, the real components through `tests/fixtures/workbench-oddkin`, the dev server over HTTP and Server-Sent Events, and the built command in a real Node process), `test/config.test.ts`, `test/examples.test.ts`, and the type-level `test/examples.types.ts`.
